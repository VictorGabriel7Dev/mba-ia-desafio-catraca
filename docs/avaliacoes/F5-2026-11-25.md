# Avaliação independente - F5 (Painel do evento)

- **Feature:** F5 - Painel do evento
- **Data:** 2026-11-25
- **Commit avaliado:** e05e9e1
- **Ferramenta:** curl (contra a stack no ar em http://localhost:4000)
- **Avaliador:** Claude (modelo Opus 4.8), contexto separado de quem implementou
- **Fonte do contrato:** `docs/specs/F5-painel.md` (C-F5-01 a C-F5-04) e `docs/specs/_CONVENCOES.md`

Cada cenário usa evento próprio da organizadora `ana.organizadora@catraca.dev`, com nome único (sufixo de timestamp), e compras da participante `carla.participante@catraca.dev`. Cartão final `0001` confirma em poucos segundos; cartão final `0003` fica pendente (aprova só em 30 a 40s), usado para manter um ingresso em `pending` durante a medição. O painel lido é `GET /api/organizer/events/:id/painel` com o Bearer da dona.

## Cenário 1 - C-F5-01 (os seis números batem com um estado conhecido)

Evento `capacity=10`, `priceCents=5000`. Compras: duas com final `0001` (confirmam) e uma com final `0003` (fica pendente). Depois, check-in de um dos confirmados.

Ingressos da carla neste evento antes do check-in (via `GET /api/me/tickets`):

```
[
  { "code": "ING-3c7c...", "status": "pending",   "checkedIn": null },
  { "code": "ING-e56d...", "status": "confirmed", "checkedIn": null },
  { "code": "ING-6471...", "status": "confirmed", "checkedIn": null }
]
```

Check-in de um confirmado:

```
POST /api/organizer/events/:id/checkin  {"codigo":"ING-e56d..."}
-> {"mensagem":"Entrada liberada","checkedIn":true,"checkedInAt":"2026-11-25T20:07:26.878Z"}
```

Painel:

```
GET /api/organizer/events/:id/painel
{
  "confirmados": 2,
  "pendentes": 1,
  "checkins": 1,
  "vagasDisponiveis": 7,
  "receitaCents": 10000,
  "estornados": 0
}
```

Esperado para o estado montado (2 confirmados, 1 pendente, 1 check-in; ocupadas = 3; capacity 10; preço 5000): confirmados=2, pendentes=1, checkins=1, vagasDisponiveis = 10 - 3 = 7, receitaCents = 2 x 5000 = 10000, estornados=0. Todos os seis números batem. **Passou.**

## Cenário 2 - C-F5-02 (confirmar incrementa Confirmados e Receita; cancelar reflete Estornados)

Evento `capacity=10`, `priceCents=3000`. Leituras sucessivas do painel (campos relevantes):

```
Painel inicial (sem compras):           {"confirmados":0,"receitaCents":0,"estornados":0}
Após 1a compra (final 0001) confirmar:  {"confirmados":1,"receitaCents":3000,"estornados":0}
Após 2a compra (final 0001) confirmar:  {"confirmados":2,"receitaCents":6000,"estornados":0}
```

Confirmados sobe 0 -> 1 -> 2 e Receita sobe 0 -> 3000 -> 6000 a cada confirmação (incremento de +1 e +3000, o preço vigente). Em seguida, cancelamento do evento:

```
POST /api/organizer/events/:id/cancel  -> {"status":"cancelled"}

GET /api/organizer/events/:id/painel
{
  "confirmados": 0,
  "pendentes": 0,
  "checkins": 0,
  "vagasDisponiveis": 0,
  "receitaCents": 0,
  "estornados": 2
}
```

Os dois ingressos que estavam `confirmed` passam a `refunded`: Estornados = 2, exatamente os que estavam confirmados. Em evento cancelado as vagas ficam em zero (R05). **Passou.**

## Cenário 3 - C-F5-03 (Vagas = lotação menos ocupadas; aumentar lotação faz subir)

Evento `capacity=5`, `priceCents=2000`. Compras: uma final `0001` (confirma) e uma final `0003` (fica pendente), ou seja, ocupadas = pending + confirmed = 2.

```
Painel com capacity=5, ocupadas=2:  {"confirmados":1,"pendentes":1,"vagasDisponiveis":3}
```

Vagas = 5 - 2 = 3, correto. Aumento da lotação por `PATCH /api/organizer/events/:id` com corpo completo e `capacity=8`:

```
PATCH ... {"...","capacity":8,"priceCents":2000}  -> {"capacity":8}

Painel após o aumento:  {"confirmados":1,"pendentes":1,"vagasDisponiveis":6}
```

Com capacity=8 e as mesmas 2 ocupadas, Vagas = 8 - 2 = 6: subiu de 3 para 6. **Passou.**

Observação (fora do contrato da F5): a rota de edição `PATCH /api/organizer/events/:id` valida o corpo inteiro do evento (name, startsAt, location, capacity, priceCents), não aceitando um corpo parcial só com `capacity`. Um PATCH apenas com `{"capacity":8}` é rejeitado e a lotação não muda. Isso é comportamento da F2 (edição), não da F5; o painel reflete corretamente a lotação efetiva em ambos os casos.

## Cenário 4 - C-F5-04 (Receita usa pricePaidCents de cada ingresso)

Evento `capacity=10`, `priceCents` inicial P1=2000. Compra 1 a P1; muda o preço para P2=7000; compra 2 a P2; confirma as duas.

```
Compra 1 (preço vigente 2000):  {"status":"pending","pricePaidCents":2000}
PATCH priceCents -> 7000:        {"priceCents":7000}
Compra 2 (preço vigente 7000):  {"status":"pending","pricePaidCents":7000}

Ingressos da carla após confirmarem:
[ {"status":"confirmed","pricePaidCents":7000},
  {"status":"confirmed","pricePaidCents":2000} ]

GET /api/organizer/events/:id/painel
{
  "confirmados": 2,
  "pendentes": 0,
  "checkins": 0,
  "vagasDisponiveis": 8,
  "receitaCents": 9000,
  "estornados": 0
}
```

Receita = 9000 = 2000 + 7000 (a soma do `pricePaidCents` de cada ingresso), e não 14000 (2 x preço atual 7000). A Receita usa o snapshot de preço de cada compra, confirmando R03. **Passou.**

## Veredito final

**APROVADO.** Os quatro itens do contrato (C-F5-01, C-F5-02, C-F5-03, C-F5-04) passaram. Os seis números do painel batem com estados conhecidos, os incrementos de Confirmados/Receita e o reflexo de Estornados no cancelamento funcionam, Vagas disponíveis acompanha a lotação, e a Receita soma o preço pago por ingresso, não o preço atual do evento.
