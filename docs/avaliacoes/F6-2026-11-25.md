# Avaliação independente F6 - API de parceiros

- **Feature:** F6 (API de parceiros)
- **Data:** 2026-11-25
- **Commit avaliado:** e05e9e1
- **Ferramenta:** curl contra o stack vivo em `http://localhost:4000`
- **Avaliador:** agente de avaliação independente Claude (Opus 4.8), contexto separado do implementador (não escreveu este código)

## Método

Cada item do contrato (C-F6-01 a C-F6-05) foi exercitado de forma independente com `curl` contra a API no ar. Os dados foram criados como a organizadora da seed (`ana.organizadora@catraca.dev`) com nomes de evento de sufixo único (`f6eval-1795637197-11717`) para não colidir com avaliadores paralelos. Foram criados quatro eventos próprios: um rascunho (DRAFT), um publicado com lotação 5 (PUB), um publicado depois cancelado (CANCEL) e um publicado com lotação 1 (CAP1). A chave de parceiro usada foi `X-Api-Key: parceiro-demo-key-123`.

## Tabela item a item

| ID | Veredito | Evidência |
|---|---|---|
| C-F6-01 | passou | Com os três eventos de mesmo sufixo (DRAFT em rascunho, PUB publicado, CANCEL publicado e depois cancelado), `GET /api/partner/events` com chave válida devolveu `HTTP 200`. Entre os eventos do meu sufixo apareceram SÓ os publicados e não cancelados: PUB (`availableSeats: 5`, lotação 5, zero compras) e CAP1 (`availableSeats: 1`). DRAFT e CANCEL não apareceram. Cada item traz exatamente as chaves `{availableSeats, id, name, priceCents, startsAt}`, sem campos a mais. |
| C-F6-02 | passou | Caminho feliz: `POST /api/partner/events/<PUB>/purchases {buyerEmail,cardNumber:4000000000000001}` devolveu `HTTP 202 {"ticketId":...,"code":"ING-...","status":"pending"}`. Ordem dos erros confirmada: cartão com 3 dígitos (`"123"`) devolveu `HTTP 422 {"error":"invalid_request"}`; corpo sem `cardNumber` devolveu `HTTP 422 {"error":"invalid_request"}`; evento rascunho (DRAFT), evento cancelado (CANCEL) e evento inexistente, todos com corpo válido, devolveram `HTTP 404 {"error":"event_not_available"}`; evento publicado cheio (CAP1, após a sua única vaga ser consumida) com corpo válido devolveu `HTTP 409 {"error":"sold_out"}`. Precedência verificada diretamente: CAP1 cheio + cartão inválido devolveu `422` (422 vence 409), e DRAFT + cartão inválido devolveu `422` (422 vence 404). Ordem 422 -> 404 -> 409 respeitada. |
| C-F6-03 | passou | `GET /api/partner/tickets/<ticketId>` de um ingresso criado pela API devolveu `HTTP 200 {"ticketId":...,"code":"ING-...","eventId":"<PUB>","status":"confirmed","checkedIn":false}`, com os campos `status` e `checkedIn` presentes. ID inexistente (`/tickets/nao-existe-999`) devolveu `HTTP 404 {"error":"ticket_not_found"}`. |
| C-F6-04 | passou | As três rotas sem `X-Api-Key` e com chave inválida (`X-Api-Key: chave-errada`) devolveram, nas seis combinações, `HTTP 401 {"error":"unauthorized"}`: `GET /api/partner/events` (sem chave e inválida), `POST /api/partner/events/<PUB>/purchases` (sem chave e inválida) e `GET /api/partner/tickets/<ticketId>` (sem chave e inválida). Na compra sem chave o 401 vence mesmo com corpo presente, confirmando a precedência 401 antes de 422. |
| C-F6-05 | passou | Após duas compras pela API no PUB (lotação 5), `GET /api/partner/events` passou a mostrar `availableSeats: 3` para o PUB, e o painel do organizador (`GET /api/organizer/events/<PUB>/painel`) refletiu `{"confirmados":2,"pendentes":0,"checkins":0,"vagasDisponiveis":3,"receitaCents":14000,"estornados":0}` (receita = 2 x 7000). O ingresso criado pela API serve ao check-in: `POST /api/organizer/events/<PUB>/checkin {codigo:"ING-..."}` devolveu `HTTP 200 {"mensagem":"Entrada liberada","checkedIn":true,...}`, e em seguida `GET /api/partner/tickets/<ticketId>` passou a mostrar `"checkedIn": true`. O worker também atuou: o ingresso de cartão final `0001` saiu de `pending` para `confirmed` sem intervenção, o que fundamenta a contagem de confirmados no painel. A compra pela API conta na lotação, no painel e no check-in exatamente como a da vitrine. |
