## Método

Cada item foi exercitado de forma independente com `curl` contra a API no ar, criando dados próprios com e-mail de sufixo aleatório (ex.: `eval_f1_fc400b80@catraca.dev`) para não colidir com outros avaliadores. A leitura de código serviu apenas para fundamentar o comportamento observado.

## Tabela item a item

| ID | Veredito | Evidência |
|---|---|---|
| C-F1-01 | passou | `POST /api/auth/register {name,email:eval_f1_fc400b80@catraca.dev,password}` devolveu `HTTP 201` com `{"user":{...,"role":"participant"},"token":...}`. `POST /api/auth/login` com as mesmas credenciais devolveu `HTTP 200` + token. `GET /api/auth/me` com `Authorization: Bearer <token>` devolveu `HTTP 200` com a identidade própria e `role:"participant"`. `POST /api/auth/logout` devolveu `HTTP 200 {"ok":true}`. Verificação extra pelo fluxo de cookie (como no browser): com cookie-jar, `GET /api/auth/me` dá `HTTP 200` antes do logout e `HTTP 401 {"error":"unauthorized"}` depois, provando que o logout encerra a sessão do cookie. |

## Observação (não bloqueante)

O logout limpa o cookie de sessão e encerra a sessão do fluxo de browser (provado acima). Como a sessão é um JWT sem estado, um token Bearer já emitido continua válido até expirar (não há revogação no servidor). Isso não contraria o C-F1-01, cujo mecanismo de sessão alvo é o cookie, e fica apenas registrado como característica do desenho.
